# Phase 7 — Product detail and wishlist · Completion report

**Date:** 2026-09-03 · **Status:** Implemented; automated acceptance green; physical sticky-bar and AR/EN visual sign-off pending

**Plan:** [`../plan.md`](../plan.md) Phase 7 · **Architecture:** [`../architecture.md`](../architecture.md)

## What was implemented

- `Review` and `ProductSpec` entities; `ReviewRepository` and `SellerRepository` ports; a
  `wishlist` domain slice with `WishlistItem`, `WishlistRepository` and `ToggleWishlistUseCase`
  (BR6); and `GetProductDetailUseCase` / `GetRelatedProductsUseCase` in the catalogue slice.
- D8 variant resolution as three pure domain functions — `resolveVariant`, `requiresVariantChoice`
  and `isInStock` — so "one variant resolves itself, anything else waits for a choice" is a rule the
  screen reads rather than one it re-implements.
- Strict Zod DTOs, mappers, data sources and HTTP repositories for reviews, sellers and the
  wishlist. `specs` now flows from the product DTO to the entity; it was validated but discarded
  before this phase.
- The PDP: paged image hero with tracking dots and a readable image counter, discount and
  out-of-stock badges, title, rating and review count, price with the variant's own price replacing
  the product's once chosen, the D8 selector, seller strip, delivery/returns panel, specification
  table, paginated reviews and the related rail — each an independent query, so a slow review page
  cannot hold back the buy bar.
- The sticky buy bar with a hint line that appears only when D8 has something to say: a variant
  still to be chosen, or a sold-out selection. Both actions are blocked in those states.
- The seller store: gradient cover, store tile pulled over it, rating / sales / product-count
  stats, the tab rule with "view all" into a seller-scoped search, and an infinite product grid.
- The wishlist screen: two-column grid with a filled remove heart over each image, price,
  add-to-cart action and the empty state with a working discover action.
- One optimistic wishlist behind `WishlistProvider`, mounted above the navigator. Every heart in
  the app — home, browse, category, search, the PDP, the seller store and the wishlist itself —
  reads the same membership set and writes through the same mutation.
- The tab bar stands down on the PDP and the seller store, which own their own bottom furniture.

## Architectural decisions

1. **`SellerRepository` is a new port** (architecture §11.4). The contract has `GET /sellers`,
   `/sellers/{id}/products` and the profile image but no `GET /sellers/{id}`, so `getById` is a
   lookup over the directory page inside the data source. The port is the shape the screen needs,
   so a real endpoint later changes one method.
2. **No use case where there is no rule.** Reviews and the seller store call their ports through
   the container directly; `GetProductDetailUseCase` exists because D8 is a policy, and
   `GetRelatedProductsUseCase` because AC7.10 is one.
3. **The wishlist is a provider, not a prop.** Membership has to be identical on every heart at
   once, so one query and one mutation sit above the navigator. Screens read it through
   `useWishlistCardProps`, and a card outside the provider simply renders no heart.
4. **Prefetch now warms the detail shape, not the bare product.** `useProductPrefetch` took a
   `ProductRepository` and wrote `catalogKeys.detail` with a `Product`; the PDP reads a
   `ProductDetail` from the same key. It now takes `GetProductDetailUseCase`, so the press-in
   prefetch is a cache hit rather than a differently shaped miss. Four screens changed prop.
5. **The seed grows a single-variant shape.** Every one of the 220 seeded products had exactly two
   variants, which made AC7.5b unreachable end to end. Every fifth product now ships in one colour
   (44 single-variant, 176 multi), leaving `product-3-default` — the only variant id any contract
   test names — untouched.
6. **`mock-server/db.json` left Prettier's scope.** It is generated by `npm run mock:reset` and
   rewritten by the mock server at runtime, so requiring Prettier formatting on it made
   `npm run verify` fail after any dev session with the mock running.

## Contract additions, recorded in `mock-server/INVENTED_ENDPOINTS.md`

- `GET /reviews/product/{id}` gains **`userName`**, resolved server-side. The collection contracts
  the route but shows no response body, and a review has to be rendered with a name; without this
  the client would issue one user request per review, the N+1 D14 already rejected for ratings.
- The same route is now **readable without a session**. Browsing is public (D3) and a guest can
  open a product page, so the reviews on it are public too. `POST /reviews` still needs a token.

## Tests added

- Domain: D8 resolution across single-variant, multi-variant, unknown-selection and stock cases;
  both new use cases; BR6 add / remove / failure and the membership id set.
- Data: review and seller mappers, including the reviewer name and the resolved profile image.
- Presentation: the PDP rendering a full product and degrading for one with no old price, discount
  or reviews; the buy bar blocked until a variant is chosen and unblocked after; single-variant
  one-tap add and buy; the seller strip opening the store; the related rail excluding the current
  product; optimistic wishlist rollback with failure reporting; guest redirection; and the wishlist
  screen's remove and empty-state paths.
- Navigation: the tab bar stands down on `Product` and `Seller` and stays up elsewhere.
- Contract: the reviews route is public and carries `userName`; both D8 variant shapes exist in the
  seed; the seller directory contains the seeded seller and an unknown seller 404s.

## Known issues and remaining risks

- **AC7.11 and AC7.15 need hardware.** The sticky bar on a notched device and with the Android
  gesture bar, and the AR/EN side-by-side, are not inferred from passing bundles or inset code.
- **Add-to-cart does not add to the cart yet.** The bar confirms with a toast; Phase 8 owns the
  mutation, the quantity guard and the totals. This is the one place the PDP is deliberately
  incomplete, and it is visible to anyone using the app.
- **A seller is read from the directory page**, not by id — see architecture §33 item 15.
- **Reviewer names depend on a mock addition** — see §33 item 14 and `INVENTED_ENDPOINTS.md`.
- **Only three products carry reviews** in the seed (`product-1` … `product-3`), which is enough to
  exercise both the populated and the empty path but is not a realistic review corpus.
- **The renderer stops mounting after four `render()` calls per test file** in this environment; a
  fifth produces a null tree. `ProductScreen.test.tsx` groups its assertions accordingly and says
  so in a comment. Worth a proper look before test files grow further.

## Handoff

Phase 8 can consume the resolved `ProductVariant` the PDP already computes (D8's `variantId` is
what `POST /cart/items` requires), the `Money` prices on both product and variant, and the wishlist
provider for the cart's own save-for-later affordances. Nothing in the discovery screens or the
transport contracts has to change.
